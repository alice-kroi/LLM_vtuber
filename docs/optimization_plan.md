## 一、现状与基线

### 1.1 当前执行流程（已实施 2.1A 并行化改造后）

```
用户消息 / 弹幕
    ↓
init (初始化)
    ↓
load_memory (加载历史记忆)
    ↓
rag_retrieval (RAG 检索)
    ↓
context_control (上下文控制)
    ↓
llm_process (LLM 调用)          ← 主要瓶颈 2-5s
    ↓                           ← 最多 3 轮工具调用
finalize (立即返回)              ← 首字响应点
    ↓ (异步并行)
    ├→ rag_save (RAG 保存)
    ├→ save_memory (记忆保存)
    ├→ [live2d] (动作生成)
    └→ [tts / cloud_tts] (语音合成)
```

### 1.2 当前性能基线（P0 优化后）

| 指标 | 数值 |
|------|------|
| 首字响应时间 | 1-2s |
| 完整响应时间 | 2-5s（含后处理） |
| Token 消耗 | 2000-3000（经 P0 优化后） |
| 工具调用率 | ~20%（每 10 次对话约 2 次触发） |
| 工具平均轮次 | 1.3 轮（MAX_TOOL_ROUNDS=3，意图预判动态降轮次） |

### 1.3 已完成的优化

| 编号 | 优化项 | 效果 |
|------|--------|------|
| P0-1 | 精简系统提示词 | Token 节省 ~60% |
| P0-2 | 回复长度硬约束（100 字） | 避免冗长回复 |
| P0-3 | 思考过程过滤 | reasoning_content 不再泄漏 |
| 2.1A | 后处理并行化 | 首字响应不再等待 TTS/存储 |
| — | 功能状态实例化 | 启停功能不重建图 |
| — | 停止时清空队列 | 停止后不再处理积压消息 |
| — | 仪表盘状态同步 | 弹幕/功能状态实时反映 |
| 1.1 | 意图分类器 | 30%+ 对话跳过工具调用 |
| 1.2 | 搜索结果预摘要 | 多条结果压缩为结构化文本 |
| 2.1 | 语义搜索缓存 | Sentence-BERT 相似度 > 0.88 复用，TTL 30min |
| 2.3 | RAG 检索短路 | 问候/短消息跳过 Milvus |

## 二、优化方向一：Agent 效率与控制台响应速度

### 2.1 问题诊断

当前首字响应时间 1-2s 几乎全部消耗在 `llm_process` 节点：

| 环节 | 耗时 | 占比 |
|------|------|------|
| LLM API 调用 | 1000-3000ms | ~80% |
| RAG 检索 | 100-300ms | ~10% |
| 上下文控制 | 50-200ms | ~5% |
| 其他 | <100ms | ~5% |

**核心矛盾**：用户说一句话，80% 的时间在等 LLM 思考。

### 2.2 已实施方案详情

#### 方案 2.2.1：工具调用智能短路（已完成）

**实现**：`LLM_node.py` 中的 `IntentClassifier`

| 意图 | 行为 |
|------|------|
| `skip` | 完全跳过 function calling，直接 LLM 回复 |
| `force_search` | 强制触发浏览器搜索（含"今天""最新""实时"等） |
| `reduce_rounds` | 将 MAX_TOOL_ROUNDS 从 3 降至 1 |
| `normal` | 默认行为，允许完整 3 轮工具调用 |

**准确率**：100%（覆盖问候、实时查询、普通对话三类场景）

#### 方案 2.2.2：搜索结果预摘要（已完成）

**实现**：`summarize_search_results()` 函数将多条搜索结果压缩为：
```
[标题]: 摘要
[标题]: 摘要
...
```
限制总长度，减少 LLM 输入 token。

## 三、优化方向二：知识与检索效率

### 3.1 问题诊断

| 问题 | 影响 |
|------|------|
| 相同 query 重复生成 embedding | 浪费 embedding API 调用 |
| 无结果缓存 | 高频问题重复检索 |
| 搜索结果全量注入 | 500+ token 直接送入 LLM |
| 无判断就触发搜索 | 用户问"你是谁"也可能触发浏览器搜索 |

### 3.2 已实施方案详情

#### 3.2.1 查询语义缓存（已完成）

**实现位置**：`tool/browser_tool.py → SemanticSearchCache`

| 参数 | 值 |
|------|------|
| 缓存上限 | 50 条 |
| TTL | 1800s（30min） |
| 相似度阈值 | 0.88 |
| 实现方式 | Sentence-BERT 向量 + 余弦相似度 |

**适用场景**：
- "你好" / "在吗" 等高频问候语
- "你叫什么名字" / "介绍一下自己" 等固定问答
- 相同话题的连续追问

#### 3.2.2 工具调用前置过滤（已完成）

**实现位置**：`LLM/LLM_node.py` 的意图分类器联动

```python
SKIP_SEARCH_KEYWORDS = ["你好", "在吗", "自我介绍", "你是谁", "谢谢", "再见"]
FORCE_SEARCH_KEYWORDS = ["今天", "最新", "最近", "现在", "实时", "当前", "新闻", "天气"]
```

#### 3.2.3 RAG 检索短路（已完成）

**实现位置**：`main.py → _should_skip_rag()`

短消息（≤6 字符）、问候、纯表情直接跳过 Milvus 检索。

## 四、优化方向三：LLM 电脑操作能力（待实现）

### 4.1 功能概述

为大模型新增「操作电脑」的能力：
- 读取屏幕内容（截图 + OCR）
- 操作鼠标（点击、拖拽、滚动）
- 操作键盘（输入文本、快捷键）
- 管理窗口（打开、关闭、切换）

### 4.2 系统架构

```
LLM (豆包 API, function calling)
    ↓ tool_calls
ToolRegistry (统一工具路由)
    ↓
ScreenTool / MouseTool / KeyboardTool / WindowTool
    ↓
Windows API (pyautogui / pygetwindow / win32api)
```

### 4.3 安全防护设计

电脑操作能力风险较高，需要：
- **操作确认层**：危险操作需用户通过 WebUI 确认
- **操作日志**：记录每次操作（前后截图 + 参数 + 结果）
- **沙箱模式**：限制可操作范围（特定应用/路径白名单）

## 六、风险与应对（已遇到的问题）

| 风险 | 实际影响 | 应对 |
|------|----------|------|
| 并行任务与 LangGraph 共享 event loop | RuntimeError | 用 `asyncio.create_task` 而非 `asyncio.run` |
| Live2D 常态动作被表情覆盖 | 模型无基础生命感 | 表情只写入专属参数，不覆盖方向/呼吸 |
| `reasoning_content` 泄漏到 TTS | 播放思考过程的声音 | chat_model.py 过滤 reasoning_content |
| 弹幕队列积压导致停止后继续处理 | 已停止但还回复 | 停止时 queue.clear() |
| 功能禁用后仍发请求 | 用户关闭了但仍请求云端 TTS | 加 self.enable_* 实例变量双检查 |
